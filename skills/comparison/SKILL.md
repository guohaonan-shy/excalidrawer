# excalidrawer comparison

对比图讲左右两边在同一组维度上有什么不同。读者的视线应该能横着一行一行扫过去：左边这一项、右边那一项，差别一眼落在眼里，不用自己在两块文字之间来回找。下面四步走：问清楚、构图、出图、对照常见画坏法检查。

## 1. 问清楚

用户的描述已经能列全这张图的全部内容（两侧的名称和完整的维度）就不问，也不去读提问规则。版式是怎么画的选择，从内容推不出来，用户没说的仍要问，选项在下面。否则先看提问的通用规则：调 skill `steps`（Claude Code 用 Skill 工具调 `excalidrawer:steps`；其他宿主读 `../steps/SKILL.md`），看它的『clarify』。这一步只读这一节，别的节和组件的参考，走到对应的那一步再读。然后问这几件事：

1. **两侧是什么，比什么**：自由文本。要的是「左侧叫什么 / 右侧叫什么」，加一组两侧都适用的维度（覆盖范围、价格、反馈深度这一类）。某一侧在某个维度上没有内容不是问题：写「无」本身就是对比的结论。
2. **版式**：单选。
   - 对称双栏，中间一个 VS：两侧同宽、逐行对齐，**推荐**。
   - 中间一列写维度名的三栏：维度名很长、单元格很短时，省得每行重复写两遍维度名。
   - 非对称：一侧要拆成几张并列的子卡，比如「两种付费方式对一种」。
3. **立场**：单选。
   - 中立：两侧权重一样，没有谁是主张方。
   - 有倾向：右侧是用户主张的一方，左侧是现状。

可选的追问：图里的文字用什么语言。默认写英文；用户的内容是中文、又没说要不要保留中文时，才问一句保留还是翻成英文，规则在 `steps` 的『出图』。

导出格式不用先问：对话里读得出图要去哪就直接定，读不出来才在出图时问一句（规则在 `steps` 的『出图』里）。用户选了哪一项、对应怎么传参，写在 `steps` 里 panel 那份参考的「用户的选择 → 参数」，这里不重复。

## 2. 构图

组件的用法：调 skill `steps`（Claude Code 用 Skill 工具调 `excalidrawer:steps`；其他宿主读 `../steps/SKILL.md`），看它的『组件』。这一步只读这一节，再读下面用到的那几份参考。

### 先把内容排成「维度」

一张对比图其实是一张画成卡片的表。动手画之前先把内容排成行：

- **一行就是一个维度，两侧都适用。** 读者是横着扫一行的，只在一侧出现的行会打断这个动作。
- **某一侧没有这个维度，也给它留一行**，填「无」「—」或「未覆盖」。「写作：无」摆在「写作：写邮件、学术讨论」旁边，就是整张图要说的话。
- **3 到 6 个维度最舒展。** 只有一两行，图说的比一句话还少；七行以上，Markdown 表格比图好读，先告诉用户这一点并提议改用表格，用户仍想要图再画。
- **同一行两侧的文字量差不多，相差不超过一半。** 左边四行、右边一行，读起来像「左边内容更丰富」，这可能不是你想表达的。要么删减，要么拆开。
- **维度的顺序在替论点说话。** 差异最鲜明的放最前，最想让读者记住的放最后。

### 一张好的对比图长什么样

标题放在最上面，点明比较的轴，而不只是两个名字：「MySpeakingScore 对 TOEFLAIR：覆盖范围」比「MySpeakingScore 对 TOEFLAIR」好。标题位置和字号是所有图共用的，在 `steps` 的参考 semantics 里。一张图只有一个轴，换一个轴就是新的一张图。几个维度并列、没有单一的轴时，标题写这组维度的统称，比如「Notion 对 Obsidian：数据、协作、离线、价格」，或者「关键差异」。

每一侧是一块带标题的容器：上面是这一侧的名字（表头），下面是它的正文。两侧的表头同高、同一条水平线；两侧同样宽，宽窄不同会让人读出偏向；中间留一条宽的缝，正中放一个 VS，是普通文字，不画圆形徽标，圆形会和卡片抢注意力。

三种版式：

```text
对称双栏                         三栏（中间写维度名）
┌── 左侧名 ──┐        ┌── 右侧名 ──┐         ┌ 左值 ┐ ┌ 维度名 ┐ ┌ 右值 ┐
│ 维度一     │   VS   │ 维度一     │         ├──────┤ ├────────┤ ├──────┤
│ 维度二     │        │ 维度二     │         └ 左值 ┘ └ 维度名 ┘ └ 右值 ┘
└────────────┘        └────────────┘

非对称（一侧拆成并列的子卡）
┌─── 左侧名 ───┐         ┌─── 右侧名 ───┐
│ 子卡一 子卡二 │   VS    │   整宽一张卡   │
│ 适合谁：…     │         │ 适合谁：…      │
└──────────────┘         └───────────────┘
```

- 对称双栏是默认，几乎所有「A 对 B」都适合。
- 三栏适合维度名本身就很长的内容：中间一列居中写维度名，不加底色或只加很浅的灰，两边的格子只写值。
- 非对称适合两边的结构本来就不一样：一侧是并列的几种做法，另一侧只有一种。两侧的外框一样宽，只有里面的拆法不同；最底下一行「适合谁」「结论」是读者最后落眼的地方，一两行就够。

### 正文有两种形态，一张图里只选一种

| 形态 | 长什么样 | 什么时候用 |
|---|---|---|
| 行卡 | 外壳里每个维度一张白卡，左右两侧同一个维度一一对应 | 每一行在两侧是**同一个维度**，读者要横着扫 |
| 单面板 | 一个透明的虚线框，文字直接写在里面，只有框的边缘左右对齐 | 每一侧是**自己的一张清单**，不是成对的行 |

判别的办法：这一行在两侧是不是同一个维度？「覆盖范围、价格、评分方式」是同一组维度，用行卡；「某产品每个任务的子分数」左边有「重复准确度」、右边有「语言运用」，同名的几项只是巧合，用单面板。给不是共同维度的行套上卡片，等于声明了一个不存在的对应关系，这是最该避免的画法。

一侧只有一两行、每行一个短语时也用单面板：盒子里再套两个盒子，装饰比内容还多。一张图里两侧要用同一种形态，左边行卡右边面板，读起来像地位有差别，而你没有这个意思。

### 用到的组件，各画出什么效果

- **panel**：每一侧一个。上面的标题区就是表头，下面是正文；外壳的大小从里面的内容算出来，不手填。两侧并排放进一个横向的 stack，缝的宽度就是两个 stack 之间的间距。
- **stack**：每一侧的正文是一列行卡。同一个维度的左右两张卡要读成一条水平线，所以两侧同一行必须一样高；一侧文字折了行，另一侧的对应卡片一起长高，整张图的行不会错位。两侧行数不同时，外框一样高，行少的一侧尾部留白，不要硬补空卡片。非对称版式里，子卡并排成一行，同行的子卡以及对面那张整宽卡一起量高。
- **形状与文字**：表头、行卡、VS 本身。文字永远居中画，不能靠对齐方式改成靠左，所以带圆点的列表只在几行都很短、长度接近时才用，否则去掉圆点，每行写成「维度：内容」。一个格子里的几行长度要接近，一般不超过四行。
- **连线**：只在表头单独画在外壳之外时才需要，从表头指向它的正文，一条短箭头。非对称版式里拆成子卡的那一侧，表头指向这一侧的外壳，不指向壳里的某一张卡。

### 配色倾向

- **中立的比较**：一侧蓝、一侧紫，线条粗细相同，没有谁更重。
- **有倾向的比较**：右侧是用户主张的一方，用蓝色，文字也跟着上蓝色，这是让一栏读成「答案」又不喧宾夺主的办法；左侧是现状，用灰色。右侧真的是终态（改造之后、修好之后）时，用绿色代替蓝色。
- **不要把另一侧涂成红色。** 红色在这套风格里读作出错，对比图一涂红就成了指责，一张诚实的图瞬间像广告。灰色说的是「现状」，更有说服力。
- 要强调时，强调获胜的一侧：它的底色用更深一档，而不是淡化另一侧。
- 一张图的颜色两个色系加墨色就够了，不再加第三种。

## 3. 出图

出图、命名、导出格式、两层质量关、迭代：调 skill `steps`（Claude Code 用 Skill 工具调 `excalidrawer:steps`；其他宿主读 `../steps/SKILL.md`），看它的『出图』。这一步只读这一节。文件名用 comparison-<对象>-<轴>，比如 comparison-speaking-apps-coverage；同一个轴、内容改了，重出到同一个文件名；换一个轴就是新的文件，不要往现有图上加一列。

## 4. 常见画坏法

| 画坏了长什么样 | 为什么 | 回到哪一步改 |
|---|---|---|
| 同一个维度，左右两张卡高矮不齐，行错位 | 一侧折行后只撑高了自己的卡 | 构图：把左右同一行量成同一个高度再画 |
| 给「同名但不是同一个维度」的清单套上了行卡 | 把巧合当成了对应关系 | 构图：改用单面板 |
| 左边行卡、右边面板，两侧形态不一样 | 图里混用了两种正文形态 | 构图：两侧统一成一种 |
| 一侧行少，被压缩或错开 | 想让两侧看上去一样长 | 构图：维度补一行「无」，别压缩 |
| VS 压到了卡片，或缝太窄 | 两栏之间留得不够 | 构图：加宽中间的缝；VS 画成纯文字 |
| 一侧涂成红色，读起来像指责 | 拿红色表示「差」 | 构图：配色，现状用灰色 |
| 两侧外框宽窄不一，读出偏向 | 一侧为了装下内容被撑宽 | 构图：两侧同宽，宽的内容缩短或折行 |
| 箭头穿过外壳的边，落在壳里的某张卡上，质量关报穿越 | 箭头连到了外壳里面的卡 | 构图：连线，连到外壳而不是壳里的卡 |
| 子卡里的价格或短语断成两截，读不通 | 子卡窄，自动折行折在了不该折的地方 | 构图：自己拆成两行，或缩短短语 |
| 一张卡折行后最后一行只剩一个孤零零的词 | 文字刚好比卡宽一点点 | 构图：微调这句文案，缩短或在合适的地方换行，让几行长度接近 |
| 一个格子里一整墙文字 | 内容太多 | 构图：一格不超过四行，更长的放到图旁的正文里 |
| 面板底下有一大块空白，两侧都有 | 面板的高度是手填的 | 构图：面板的高度从内容算，不手填 |
| 七个以上维度，图拥挤且没信息增量 | 维度太多 | 问清楚：提议改成 Markdown 表格 |
| 出图后质量关有警告，或看图有一条不过 | 以上任一条没排掉 | 按 `steps`『出图』里的两层质量关逐条修，再出一遍 |
