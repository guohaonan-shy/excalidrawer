# excalidrawer architecture

画架构图：系统分哪几层、每层有哪些服务、层与层之间谁依赖谁。下面四步走，走到「怎么做」那一步才去调 `steps`，开场不用整份读。

## 1. 问清楚

**用户的描述已经能列全这张图的全部内容（有哪几层、每层有哪些服务）就不问，也不去读提问规则。** 否则先看提问的通用规则（一轮问几题、什么时候用选择题）：调 skill `steps`（Claude Code 用 Skill 工具调 `excalidrawer:steps`；其他宿主读 `../steps/SKILL.md`），看它的『clarify』。这一步只读这一节。然后问这三件：

1. **系统核心组成**：自由文本，让用户把组成列出来，由你按层归。
2. **结构形态**：单选。
   - 经典分层：每层一条横带，服务在带里排成一行。默认。
   - 分层加子分组：一层之内再分几个小带，比如前端层分 Web 和 Mobile 两个。
   - 自由拓扑：不分上下层，服务按分组或围着一个中心摆，靠连线说明关系。
3. **是否画连线**：单选。
   - 纯拓扑不画线：只靠分层的结构讲故事。默认。
   - 画关键流：3–5 条主流。
   - 画完整连线：慎选，线一多就成蜘蛛网。

可选追问：有没有 API Gateway、消息队列、Service Mesh 这类应该单独成一层的东西。选了画连线时，哪些调用是异步的、哪些服务是计划中的，用户没说就问，不要猜：虚线猜错了比没有虚线更误导。

这几个选项各自落到哪些组件上，第 2 步调 `steps` 时在 panel 那一份里有对照。

导出格式不用先问：对话里读得出图要去哪就直接定，读不出来才在出图时问一句（规则在 `steps` 的『出图』里）。

## 2. 构图

**一张好的架构图讲清三件事**：系统分几层、每层的职责是什么、请求和数据大致从哪层流到哪层。读者扫一眼就能说出「入口在哪、数据落在哪」。

### 先把分层建对

摆任何东西之前先过一遍分层：

- API Gateway、消息队列 / Broker、Service Mesh / Sidecar 通常各自值得单独一层，不是「又一个后端服务」。把它们塞进业务层，连线会被迫穿过同一行的其他服务，扇出难看。
- 一层只有一个服务没问题（比如单独一个网关），不要为了凑齐补格子。
- 纯拓扑的图每层可以多放几个服务；带连线的图每层少放，线才走得开。
- 每层以 4 个服务以内最舒服；超过就考虑拆成子分组，或把这一层拆成两层。

### 三种布局

**经典分层**：每层一条横带，上下叠放，各层同宽。带的左边是一列层名，右边是这一层的服务，一行排开。适合层次清晰、线性往下的系统。

**分层加子分组**：整体还是上下叠放的层，但某一层里再分几个并排的小带，每个小带有自己的名字和条目。适合一层之内有明显的两三类东西，且这些分类本身值得被读者看见。

```text
┌──────────┐ ┌──────────────────┐ ┌──────────────────┐
│ Frontend │ │ Web Frontend     │ │ Mobile Frontend  │
│  (层名)  │ │ [React] [Admin]  │ │ [iOS] [Android]  │
└──────────┘ └──────────────────┘ └──────────────────┘
```

**自由拓扑**：没有清晰的上下层，服务之间多对多地依赖。按分组成块摆，或一个中心加几个外围；这时连线本身就是内容，要画。

### 用到的组件，各画出什么

- **panel**：一层就是一个 panel。层名放在左边一列，右边是服务；子分组时每个小带也是一个 panel，层名在上。**层名只是文字，不画外框**：它站在层的浅底色上，没有自己的矩形。效果：每层的高度跟着里面的内容走，服务标签折行了层也不会溢出；所有层右边缘对齐，层名那一列同宽，内容区的左边缘齐整。
- **stack**：一层里的服务排成一行。效果：同一层的服务取同一个高度，长标签折行了也不会只有一个格子变高，整层读成一条齐平的带；服务在带里居中铺开，不左挤右空、也不贴在顶上。服务不只是一行标签、还带标题加几条要点时，用带标题的格子，不要手填高度。
- **形状与文字**：每个服务一个圆角矩形，层的外壳是浅底色的矩形；层名是不带框的文字。
- **连线**（只在第 1 步选了画连线时用）：从上一层服务的下边中点出，进下一层服务的上边中点，出入点不为了拉直而偏移；两个服务上下不对齐时，直角折线自己在层间的空隙里拐成带圆角的 Z 形。一个源连几个目标、或几个源汇到一个目标时，共用中点这个出入点，不摊开。层与层之间的空隙要比不画连线时宽，留够箭头的长度、折线拐弯和标签的位置。用户点名了具体的服务就连那个服务本身，只要线不穿过别的框；目标是外壳里一堆卡片、没有点名时，连外壳，不连里面的卡。
- **legend**：用了自定义的线型含义（虚线 = 异步、虚线框 = 计划中）时放一个图例，三行以内。
- **标题**：一张图一个标题，点明这是什么系统的什么视图；标题的字号和位置是全图共用的值，不在这里写，在 `steps` 的 semantics 那一份里。

组件的参数和它们怎么配合，调 skill `steps`（Claude Code 用 Skill 工具调 `excalidrawer:steps`；其他宿主读 `../steps/SKILL.md`），看它的『组件』。这一步只读这一节，再读用到的那几份参考：形状与文字、panel、stack、连线、semantics（线型、颜色含义在里面）；用了自定义线型或颜色含义时再加 legend。

### 配色

一层一个色系，层与层不同色，同一层里外壳用浅色、服务用同色系的中间色，整张图的视觉语法才一致。默认的轮转：

| 层 | 色系 |
|---|---|
| 表现层 | 蓝 |
| 网关 / 中间件 | 紫 |
| 业务 | 绿 |
| 数据 | 黄 |
| 辅助（监控、基础设施等） | 灰或橙 |

整张图不超过四种颜色；红色只留给真正的错误，不拿来强调正常的层。

### 连线的约定

- **没选连线就一条都不画**，分层的结构自己会讲故事。
- 同步调用用实线，异步（队列、事件、webhook）用虚线，计划中的服务用虚线框加虚线连线。**一张图里虚线只表达一种意思**，并配图例；不确定哪些是异步，回第 1 步问。
- 带连线的图，互相连接的服务可以跨层放在同一列，线就是一条竖线。各层的服务仍在带里居中，不为了对齐把整层推向一边；对不齐时，先调服务的次序，仍然对不齐就让直角折线自己拐成 Z 形，**不去偏移连线的出入点**：线永远从服务的中点出、进服务的中点。用户列的服务次序没有先后含义时，可以为了对齐重排；次序本身有含义（比如调用链的先后）就保持，宁可线拐一下。

## 3. 出图

调 skill `steps`（Claude Code 用 Skill 工具调 `excalidrawer:steps`；其他宿主读 `../steps/SKILL.md`），看它的『出图』，这一步只读这一节：文件命名（架构图是 `architecture-<名字>`）、导出格式、两层质量关和迭代都在那里。两关都过才算画完。

## 4. 常见画坏法

- **每层的服务挤在带的左边、右边空着一大块**：整条带读成头重脚轻。回第 2 步，服务在带里居中铺开。
- **同一层的服务高矮不一**：某个服务标签长，折行后只有它自己变高，一条带就参差了。回第 2 步，同层服务取同一个高度。
- **API Gateway 埋在业务层**：从网关出去的线要穿过同一行的服务。回第 2 步的「先把分层建对」，给它单独一层。
- **连线没有从服务的中点出入**：为了拉直把出入点偏到了边上，读者看不出线连的是哪个服务。回第 2 步，出入点回到中点，对不齐就让折线拐 Z 形。
- **服务一律靠左挤、线乱窜**：带连线的图没有照连线摆位。回第 2 步，能同列的互相连接的服务跨层同列，其余让折线自己拐。
- **层名外面套了一个矩形**：读成又一个服务，层的结构被打乱。回第 2 步，层名只画文字。
- **只有一个服务的层孤零零地靠在宽带的左边**：上层来的线要扫过一大段空白才到它。回第 2 步，居中放在它所连的服务上方；纯拓扑时居中放在带里。
- **子分组的名字压着第一个服务**：名字和条目之间要留出呼吸。回第 2 步，子分组一律用 panel，不手摆名字。
- **各层的层名那一列宽窄不一**：内容区的左边缘就错开了。回第 2 步，所有层的层名列取同一个宽度。
- **层与层挤在一起，箭头只剩一个头**：画了连线却没放宽层间的空隙。回第 2 步，放宽后再渲染。
- **跨层的线走成横向或斜向**：自动选边在水平差大时会选水平。回第 2 步，明确让它从下边出、上边进。
- **虚线一张图里表两种意思**：读者没法判断虚线是异步还是计划中。改成一个用虚线、另一个换颜色，并配图例。
- **颜色超过四种、或连线五颜六色**：显得花，颜色抢了结构的戏。回第 2 步的配色，连线默认墨色，只在颜色承载含义时才上色。
