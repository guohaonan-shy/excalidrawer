# excalidrawer architecture

画架构图：系统分哪几层、每层有哪些服务、层与层之间谁依赖谁；或者换一个角度，数据从哪来、经过哪几段、到哪去（数据全景）。下面四步走，走到「怎么做」那一步才去调 `steps`，开场不用整份读。

## 1. 问清楚

**用户的描述已经能列全这张图的全部内容就不问，也不去读提问规则**：分层要说全有哪几层、每层有哪些服务；数据全景要说全有哪几段、每段里有哪些系统、有没有贯穿各段的能力。否则先看提问的通用规则（一轮问几题、什么时候用选择题）：调 skill `steps`（Claude Code 用 Skill 工具调 `excalidrawer:steps`；其他宿主读 `../steps/SKILL.md`），看它的『clarify』。这一步只读这一节。

先定这张图讲什么，再问内容：

0. **讲调用关系，还是讲数据流向**：单选。
   - 调用关系（分层）：谁依赖谁，层上下叠放。下面三种结构形态都属于它。
   - 数据流向（全景）：数据往哪流，段左右排开，只画段与段之间的流向。

   **用户的话已经说明的不问**：说了「数据全景」「数据栈全景」「data stack」「high-level」、或者要从数据源画到消费端，就是全景；说了分层、三层架构、微服务、服务拓扑、谁调用谁，就是分层。两边的信号都没有（只说「画个系统架构图」）才问。

选了**分层**，接着问这三件：

1. **系统核心组成**：自由文本，让用户把组成列出来，由你按层归。
2. **结构形态**：单选。
   - 经典分层：每层一条横带，服务在带里排成一行。默认。
   - 分层加子分组：一层之内再分几个小带，比如前端层分 Web 和 Mobile 两个。
   - 自由拓扑：不分上下层，服务按分组或围着一个中心摆，靠连线说明关系。
3. **是否画连线**：单选。
   - 纯拓扑不画线：只靠分层的结构讲故事。默认。
   - 画关键流：3–5 条主流。
   - 画完整连线：慎选，线一多就成蜘蛛网。

可选追问：有没有 API Gateway、消息队列、Service Mesh 这类应该单独成一层的东西。选了画连线、而且这一轮本来就要提问时，顺带问哪些调用是异步的、哪些服务是计划中的；不为这两件事单独多问一轮。用户没交代的，一律画实线，服务画实线框。

用户把层和服务说全了、这一步整个跳过时，结构形态取经典分层；连线按用户在描述里说的画，没提就不画；同样没有同步异步和计划中的交代，同样一律实线。

选了**全景**，结构形态和是否画连线都不用问：形态就是第四种布局，段与段之间的箭头总是画，段内系统之间的连线总是不画。只问内容，一题自由文本：

- **有哪几段、每段里有哪些系统、有没有贯穿各段的横带**（治理、监控、权限这类）。用户没列全时，把数据栈的通行分段当作建议写进问题里让用户改：数据源 → 采集 → 存储 → 计算 → 消费，每段各列两三个常见系统，横带写治理、监控、权限。用户只说「画个数据栈全景」、没有别的内容时就这样问；用户回「按常见的画」就照建议画。

分层的这几个选项各自落到哪些组件上，第 2 步调 `steps` 时在 panel 那一份里有对照；全景用到的组件和它们画出的效果，在第 2 步的「数据全景」一节。

导出格式不用先问：对话里读得出图要去哪就直接定，读不出来才在出图时问一句（规则在 `steps` 的『出图』里）。

## 2. 构图

**一张好的架构图讲清三件事**：系统分几层、每层的职责是什么、请求和数据大致从哪层流到哪层。读者扫一眼就能说出「入口在哪、数据落在哪」。

**数据全景是另一种讲法**：不讲谁调用谁，讲数据往哪流，读者扫一眼能说出「数据从哪来、一路经过哪几段、最后给了谁」。它是第四种布局，写在「三种分层布局」之后；第 1 步选了全景就跳到那一节，下面「先把分层建对」「配色」「连线的约定」都只管分层。

### 先把分层建对（分层的三种布局）

摆任何东西之前先过一遍分层：

- API Gateway、消息队列 / Broker、Service Mesh / Sidecar 通常各自值得单独一层，不是「又一个后端服务」。把它们塞进业务层，连线会被迫穿过同一行的其他服务，扇出难看。
- 一层只有一个服务没问题（比如单独一个网关），不要为了凑齐补格子。
- 纯拓扑的图每层可以多放几个服务；带连线的图每层少放，线才走得开。
- 每层以 4 个服务以内最舒服；超过就考虑拆成子分组，或把这一层拆成两层。

### 三种分层布局

**经典分层**：每层一条横带，上下叠放，各层同宽。带的左边是一列层名，右边是这一层的服务，一行排开。适合层次清晰、线性往下的系统。

**分层加子分组**：整体还是上下叠放的层，但某一层里再分几个并排的小带，每个小带有自己的名字和条目。适合一层之内有明显的两三类东西，且这些分类本身值得被读者看见。

```text
┌──────────┐ ┌──────────────────┐ ┌──────────────────┐
│ Frontend │ │ Web Frontend     │ │ Mobile Frontend  │
│  (层名)  │ │ [React] [Admin]  │ │ [iOS] [Android]  │
└──────────┘ └──────────────────┘ └──────────────────┘
```

**自由拓扑**：没有清晰的上下层，服务之间多对多地依赖。按分组成块摆，或一个中心加几个外围；这时连线本身就是内容，要画。

### 分层用到的组件，各画出什么

- **panel**：一层就是一个 panel。层名放在左边一列，右边是服务；子分组时每个小带也是一个 panel，层名在上。**层名只是文字，不画外框**：它站在层的浅底色上，没有自己的矩形。效果：每层的高度跟着里面的内容走，服务标签折行了层也不会溢出；所有层右边缘对齐，层名那一列同宽，内容区的左边缘齐整。
- **stack**：一层里的服务排成一行。效果：同一层的服务取同一个高度，长标签折行了也不会只有一个格子变高，整层读成一条齐平的带；服务在带里居中铺开，不左挤右空、也不贴在顶上。服务不只是一行标签、还带标题加几条要点时，用带标题的格子，不要手填高度。
- **形状与文字**：每个服务一个圆角矩形，层的外壳是浅底色的矩形；层名是不带框的文字。
- **连线**（只在第 1 步选了画连线时用）：从上一层服务的下边中点出，进下一层服务的上边中点，出入点不为了拉直而偏移；两个服务上下不对齐时，直角折线自己在层间的空隙里拐成带圆角的 Z 形。一个源连几个目标、或几个源汇到一个目标时，共用中点这个出入点，不摊开。层与层之间的空隙要比不画连线时宽，留够箭头的长度、折线拐弯和标签的位置。用户点名了具体的服务就连那个服务本身，只要线不穿过别的框；目标是外壳里一堆卡片、没有点名时，连外壳，不连里面的卡。
- **legend**：用了自定义的线型含义（虚线 = 异步、虚线框 = 计划中）时放一个图例，三行以内。
- **标题**：一张图一个标题，点明这是什么系统的什么视图；标题的字号和位置是全图共用的值，不在这里写，在 `steps` 的 semantics 那一份里。

组件的参数和它们怎么配合，调 skill `steps`（Claude Code 用 Skill 工具调 `excalidrawer:steps`；其他宿主读 `../steps/SKILL.md`），看它的『组件』。这一步只读这一节，再读用到的那几份参考：形状与文字、panel、stack、连线、semantics（线型、颜色含义在里面）；用了自定义线型或颜色含义时再加 legend。

### 数据全景：左到右的第四种布局

**它讲什么**：数据从哪来、经过哪几段、到哪去的端到端一张图，比如「数据源 → 采集 → 存储 → 计算 → 消费」。

**什么时候选它**：读者要看的是数据一路怎么流，段与段有先后；段里的系统只是这一段「有哪些」，彼此没有调用关系要讲。要讲的是谁调用谁、层上下叠放、服务之间画调用，选前三种分层布局；一张图里两样都想要，先画数据全景，调用关系另画一张分层，不要揉在一起。

```text
  Sources          Ingest           Storage          Compute          Consume
┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
│ App logs │     │ Kafka    │     │ S3 lake  │     │ dbt      │     │ BI       │
│ CRM      │ ━━▶ │ Fivetran │ ━━▶ │ Snowflake│ ━━▶ │ Spark    │ ━━▶ │ ML       │
│ Payments │     │          │     │          │     │          │     │ Rev. ETL │
└──────────┘     └──────────┘     └──────────┘     └──────────┘     └──────────┘
┌─────────────────────────────────────────────────────────────────────────────┐
│            Governance · Monitoring · Access (spans every stage)             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**各组件在这里画出什么**：

- **panel**：每一段一个 panel，从左到右排成一行，段名在 panel 顶上。效果：所有段一样高（取最高那一段的高度，系统少的段下面留白，不补格子凑数），也一样宽（宽度定成一个固定的值，段名比系统名长时也不撑宽自己），间隔均匀；段名折行了段也不会溢出。段是同一条数据链上的几个环节，不是不同职责的层，所以各段的外壳和描边用同一个色系，不是一段一个颜色。
- **stack**：一段里的系统竖排成一列，是 panel 里的内容区。效果：同一列的系统同宽、居中对齐，段里系统多了列自己长高，不压到段名；长名字折行时只有它自己变高。整排段本身也是一个横排的 stack，段与段之间留够放箭头的空隙。
- **连线**：段与段之间一条粗箭头，从前一段右边的中点出、进后一段左边的中点，笔直、横平；整张图只有这几条线，所以用粗线是合适的（粗线只给主路径，这里整条数据链就是主路径）。**不画段内系统之间的连线**：一旦要画系统之间的连线，这张图就是分层或自由拓扑，回到前三种布局。段间的空隙要比分层的层间更宽，留够箭头的长度，箭头不压到 panel 的边框。
- **贯穿横带**：治理、监控、权限这类贯穿每一段的能力画成整排下方的一条横带，写一行文字。效果：横带的左右边缘和整排的左右边缘对齐，宽度就是整排的宽度；它和整排之间留一段空隙，不贴着。没有这类能力就不画，不为凑齐加一条。横带换一个色系（比如整排蓝、横带紫），读成另一类东西。
- **标题**：一张图一个标题，点明这是什么系统的什么视图，居中在整排上方；标题的字号和位置是全图共用的值，不在这里写，在 `steps` 的 semantics 那一份里。

组件的参数和它们怎么配合，调 skill `steps`（Claude Code 用 Skill 工具调 `excalidrawer:steps`；其他宿主读 `../steps/SKILL.md`），看它的『组件』。这一步只读这一节，再读用到的那几份参考：形状与文字、panel（段和横带）、stack（整排与每段里的一列，嵌套和同高同宽的写法在那里）、连线、semantics；不需要 legend，除非用户给箭头或系统加了自定义含义。

**段数和每段的系统数**：段 3 到 6 个读得最清楚，更多就合并相邻的段；每段 2 到 4 个系统，超过 5 个就考虑把这一段拆成两段。

### 配色（分层）

一层一个色系，层与层不同色，同一层里外壳用浅色、服务用同色系的中间色，整张图的视觉语法才一致。默认的轮转：

| 层 | 色系 |
|---|---|
| 表现层 | 蓝 |
| 网关 / 中间件 | 紫 |
| 业务 | 绿 |
| 数据 | 黄 |
| 辅助（监控、基础设施等） | 灰或橙 |

整张图不超过四种颜色；红色只留给真正的错误，不拿来强调正常的层。

### 连线的约定（分层）

- **没选连线就一条都不画**，分层的结构自己会讲故事。
- 同步调用用实线，异步（队列、事件、webhook）用虚线，计划中的服务用虚线框加虚线连线。**一张图里虚线只表达一种意思**，并配图例；用户没交代哪些是异步、哪些是计划中，不猜，一律实线，虚线猜错了比没有虚线更误导。
- 带连线的图，互相连接的服务可以跨层放在同一列，线就是一条竖线。各层的服务仍在带里居中，不为了对齐把整层推向一边；对不齐时，先调服务的次序，仍然对不齐就让直角折线自己拐成 Z 形，**不去偏移连线的出入点**：线永远从服务的中点出、进服务的中点。用户列的服务次序没有先后含义时，可以为了对齐重排；次序本身有含义（比如调用链的先后）就保持，宁可线拐一下。

## 3. 出图

调 skill `steps`（Claude Code 用 Skill 工具调 `excalidrawer:steps`；其他宿主读 `../steps/SKILL.md`），看它的『出图』，这一步只读这一节：文件命名（架构图是 `architecture-<名字>`）、导出格式、两层质量关和迭代都在那里。两关都过才算画完。

## 4. 常见画坏法

- **每层的服务挤在带的左边、右边空着一大块**：整条带读成头重脚轻。回第 2 步，服务在带里居中铺开。
- **同一层的服务高矮不一**：某个服务标签长，折行后只有它自己变高，一条带就参差了。回第 2 步，同层服务取同一个高度。
- **API Gateway 埋在业务层**：从网关出去的线要穿过同一行的服务。回第 2 步的「先把分层建对」，给它单独一层。
- **连线没有从服务的中点出入**：为了拉直把出入点偏到了边上，读者看不出线连的是哪个服务。回第 2 步，出入点回到中点，对不齐就让折线拐 Z 形。
- **服务一律靠左挤、线乱窜**：带连线的图没有照连线摆位。回第 2 步，能同列的互相连接的服务跨层同列，其余让折线自己拐。
- **层名外面套了一个矩形**：读成又一个服务，层的结构被打乱。回第 2 步，层名只画文字。
- **只有一个服务的层孤零零地靠在宽带的左边**：上层来的线要扫过一大段空白才到它。回第 2 步，居中放在它所连的服务上方；纯拓扑时居中放在带里。
- **子分组的名字压着第一个服务**：名字和条目之间要留出呼吸。回第 2 步，子分组一律用 panel，不手摆名字。
- **各层的层名那一列宽窄不一**：内容区的左边缘就错开了。回第 2 步，所有层的层名列取同一个宽度。
- **层与层挤在一起，箭头只剩一个头**：画了连线却没放宽层间的空隙。回第 2 步，放宽后再渲染。
- **跨层的线走成横向或斜向**：自动选边在水平差大时会选水平。回第 2 步，明确让它从下边出、上边进。
- **虚线一张图里表两种意思**：读者没法判断虚线是异步还是计划中。改成一个用虚线、另一个换颜色，并配图例。
- **颜色超过四种、或连线五颜六色**：显得花，颜色抢了结构的戏。回第 2 步的配色，连线默认墨色，只在颜色承载含义时才上色。

### 数据全景特有的

- **各段高矮宽窄不一**：系统多的段把自己撑高、段名长的段把自己撑宽，别的段还是原来的样子，一排参差，箭头也不再落在同一条水平线上，段间空隙长短不一。回第 2 步的「数据全景」，整排的段取同一个高度和同一个宽度，系统少的段留白。
- **段间箭头压到 panel 上，或只剩一个箭头头**：段与段的空隙留得太窄，箭头伸进了段的边框。回第 2 步，放宽段间空隙后再渲染，箭头从一段的右边框外出发、到下一段的左边框外为止。
- **横带和整排不一样宽**：横带只盖了前几段，或者比整排还长出一截。回第 2 步，横带的左右边缘对齐整排的左右边缘。
- **段内画了系统之间的连线**：线一多，数据流向被调用关系淹没，读者分不清该看段间的箭头还是段内的线。回第 1 步，要讲调用关系就改选分层，全景里只留段间的箭头。
- **每段一个颜色**：五段五种颜色，颜色抢了流向的戏，也超过四种。回第 2 步，段用同一个色系，只有横带换色。
